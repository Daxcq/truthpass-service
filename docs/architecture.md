# TruthPass 架构

## 一句话定位

TruthPass 是白牌电商采购 Agent 的服务可靠性层：它帮助 Agent 选择陌生服务、验收真实交付，并把结果沉淀为可被其他 Agent 查询的公共信誉。

## 产品分层

讨论中形成了两层边界：

- **TruthPass 真验**是基础设施，提供服务注册、实时探测、任务验收、证据锚定和公共信誉 API/Skill；
- **OpenGoods 透明货**是未来的应用层，负责把白牌商品的原材料、工序、质检、出厂和物流记录组织成可查询的商品档案。

用户自己的 Agent 负责理解“我想买什么”，TruthPass 负责回答“哪些服务和商品证据值得信任”。

## 为什么白牌电商适合作为场景

白牌品牌通常同时依赖供应商、检测机构、物流和售后服务。采购 Agent 不能因为服务拥有链上身份或历史评分，就假设它当前在线、数据准确或一定能履约。因此，商品批次是任务载荷，服务提供者才是被评价对象。

白牌不等于所有生产资料都必须公开。公开的是可验证的质量结论、检测证明和履约摘要；商业配方、个人信息和需要保密的原始资料仍应留在链下并按权限提供。

## 四步闭环

1. **声明**：服务登记身份、能力、端点和签名地址。
2. **探测**：检查健康状态、能力匹配、响应格式和小型挑战任务。
3. **验收**：比较任务、批次、时间、签名、物流中断等确定性条件。
4. **沉淀**：将任务级反馈、证据哈希和撤销状态写入公共信誉登记表。

## Agent 边界

- Planner Agent 将采购目标拆成验收标准。
- Probe Agent 调用健康检查和挑战接口。
- Verifier 使用确定性规则判断通过、拒绝或部分完成。
- Router Agent 按实时状态和验收分数选择服务。
- Reputation Agent 生成反馈并提交链上锚定。

大模型负责规划、解释和补充问题；通过与拒绝由规则引擎决定，避免把关键判断交给不可复现的自由文本。

## 评分建议

```text
可靠性 = 历史履约 25% + 当前可用性 20% + 本次任务验收 55%
```

反馈必须绑定任务哈希、服务身份和证据哈希。同一个调用者对同一任务只能反馈一次，近期记录权重更高，撤销记录不再计入聚合。

## 链上与链下边界

链上：服务 ID、钱包地址、任务哈希、证据哈希、评分、状态、时间戳、撤销状态。

链下：检测报告全文、图片、传感器明细、物流轨迹、商业隐私和个人信息。

## BOT Chain 部署

合约目标网络为 BOT Chain Mainnet，Chain ID 为 677。比赛 MVP 使用 `contracts/TrustRegistry.sol`，后续可增加 ERC-8004 注册表适配器。

## 现实数据的可信边界

区块链只能保证提交过的记录、身份和时间没有被悄悄改写，不能单独证明工厂提交的数据真实。现实确认需要多个来源共同提供：第三方检测 Agent、平台控制的传感器、物流记录和人工抽检。Agent 负责交叉核验，链上负责留下可复核的结果。
